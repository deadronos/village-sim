# IDEA: An autonomous village that thinks on a timer

**One paragraph.** Build a headless, deterministic village simulation in which
every inhabitant — farmer, baker, innkeeper, guard, child — runs its own day:
working its trade, buying supplies, eating, resting, visiting the tavern, talking
to neighbours. Their *choices* come from a pluggable **typed decision provider**
(a local System One model such as Kev/Jev by default), asked in batches on a
timer; their *world* — money, stock, location, recipes, arithmetic — is plain
deterministic code. The point is to watch a small economy and social fabric
sustain itself without a chat model writing anything.

This document is a build brief. It is deliberately implementation-agnostic:
TypeScript, Python, Rust or Go are all fine. The contract and acceptance
criteria are what matter.

---

## 1. Goals

1. An autonomous simulation that runs N simulated days without intervention and
   produces an observable, legible story ("the baker ran out of wheat on day 2
   because the farmer spent the morning at the tavern").
2. Behaviour decided by an **external typed-decision endpoint**, swapable by
   configuration, with a scripted fallback that needs no model at all.
3. **Deterministic and replayable**: same seed → identical run; every decision
   auditable with its probability distribution.
4. Cheap enough to leave running: decisions are batched, gated and rate-limited,
   not called per frame.

## 2. Non-goals (explicitly out of scope)

- Graphics, physics, pathfinding meshes, sound.
- Free-text dialogue generated by an LLM. Optional stretch only, behind a flag.
- Networking, multiplayer, persistence to a database (JSON files are enough).
- Realism. This is a legible toy economy, not an economic simulation.

## 3. The non-negotiable rule

> **The model picks intent; deterministic code owns state, arithmetic,
> constraints and gating.**

The provider returns probabilities over labelled options. It never adds gold,
never checks stock, never moves an entity. Every returned action is validated
against the world before it is executed; an infeasible action is rejected and
the entity falls back to a safe action for that tick.

Two corollaries, both learned the hard way (see §12):

- **Gate the option set.** Never offer every action at every step. An ungated
  4B model collapses into the two lowest-commitment options ("wander", "rest")
  and the village idles.
- **Sample, don't argmax.** Draw from the returned distribution with a seeded
  RNG. Argmax turns eight villagers into eight clones.

## 4. Architecture

```
                    +-----------------------+
   tick loop ------>|  Decision Scheduler   |---- batch ----> DecisionProvider
   (sim clock)      |  gating + question    |                      |
                    |  building             |<--- probabilities ---+
                    +-----------+-----------+
                                | sampled intents
                                v
                    +-----------------------+
                    |  Deterministic World  |
                    |  economy, movement,   |
                    |  needs, invariants    |
                    +-----------+-----------+
                                |
                                v
                       decisions.jsonl + state hashes
```

## 5. Decision provider contract (the agnostic bit)

### 5.1 Interface

```
interface Question:
    type: "choice" | "noul" | "score"
    instructions: string
    criteria: map<string,string>   # choice: label -> description
             | {true,false}         # noul
             | string[2..255]       # score, ordered

interface Answer:
    type: "choice" | "noul" | "score"
    choice?: string
    noul?: number            # P(true)
    score?: number           # expected position on the scale
    probabilities: map<string, number>   # required for choice & score
    confidence?: number

interface DecisionProvider:
    decide(state: string|object, questions: map<string, Question>, seed: int)
        -> map<string, Answer>
```

Providers must return **probabilities**; convenience scalars (`choice`, `noul`,
`score`) are logged but never branched on.

### 5.2 Configuration (env or config file; env wins)

```
DECISION_PROVIDER   = systemone | scripted | replay      (default: scripted)
DECISION_ENDPOINT   = http://127.0.0.1:8009/v1/systemone
DECISION_MODEL      = kev-latest
DECISION_TIMEOUT_MS = 120000
DECISION_BATCH      = auto | always | never              (default: auto)
DECISION_SAMPLE     = weighted | argmax                 (default: weighted)
DECISION_ESCALATE_ON = sampled | margin | entropy       (default: sampled)
DECISION_MIN_CONF   = 0.34       # below this, escalate (see §7.3)
DECISION_API_KEY    = (optional) bearer token, sent only if set
```

Swapping providers must require **no code change**. That is acceptance criterion
A5.

### 5.3 System One wire format

Request:

```json
{
  "model": "kev-latest",
  "state": "shared world summary, or a JSON object",
  "questions": {
    "act_anna": {
      "type": "choice",
      "instructions": "anna the baker, at the bakery. Gold 9g, no wheat...",
      "criteria": {"work": "bake bread", "restock": "get supplies",
                   "buy_food": "eat", "socialize": "talk", "rest": "recover"}
    }
  }
}
```

Response (only the parts that matter):

```json
{"answers": {"act_anna": {"type": "choice", "choice": "work",
  "confidence": 0.61,
  "probabilities": {"work": 0.61, "restock": 0.22, "buy_food": 0.09,
                    "socialize": 0.06, "rest": 0.02}}},
 "latency_ms": 812}
```

Notes that cost time if ignored:

- `GET /v1/models` is the health check. A bare `GET /` returns 404 — normal.
- On FastAPI servers, `GET /openapi.json` is the authoritative schema; fields
  drift between builds.
- `model` is echoed, not validated. Pin the alias in config; an unknown name may
  still answer.
- If the endpoint requires HTTPS or a key, that belongs in the provider, not in
  call sites.
- Keep `state` short. The 4B Kev build accepts 8K tokens but was trained on
  ≤384 state tokens; ~60–120 tokens per call is the sweet spot.

### 5.4 Batching

- **One call = one state + N questions**, one question per entity:
  `act_<entity_id>`.
- `DECISION_BATCH=auto`: batch when ≥2 entities need a decision this tick;
  otherwise single question.
- If a batched call fails, retry once per-entity (bounded, exponential backoff),
  then use scripted fallback for questions without usable answers.
- Three consecutive sweeps without usable answers activate scripted fallback
  and publish a warning to the live viewer. Retry on the first decision sweep
  after five seconds. Any usable answer restores System One and resets the
  failure streak.

Measured on a 4B Kev model (Apple M4, MPS) — use these to size the loop:

| Questions per call | Latency | Throughput |
|---|---|---|
| 1 (5 questions about one entity) | 0.96 s | ~1.0 /s |
| 6 entities | 1.35 s | 4.4 /s |
| 12 entities | 1.86 s | 6.5 /s |
| 24 entities | 3.48 s | 6.9 /s |

Throughput **plateaus near 7 decisions/s**. Scale by deciding less often, not
by batching harder.

## 6. World model

### 6.1 Places

A small graph of named places: `well, bakery, tavern, market, fields, woods,
smithy, garden`, plus one `home_<id>` per entity. Each edge has a travel cost in
ticks (1 for the reference version; a real graph is a stretch goal).

### 6.2 Entity

```
id, role, title
home, workplace, location
gold
inventory: map<item, qty>
needs: { hunger 0..1, energy 0..1, social 0..1 }
focus: duty | earn | socialize | rest        (set once per day)
goal: { kind, target, ticks_left } | null
memory: ring buffer of ≤4 short strings
affinity: map<entity_id, number>
```

Needs decay each tick (reference: hunger +0.035, energy −0.02, social −0.015).
Clamp to 0..1.

### 6.3 Memory

The provider is stateless, so the entity's "memory" is whatever the serialiser
writes into `instructions`. Keep a ring buffer of short event strings ("sold 2
bread to bram", "nothing to restock with"). **This serialiser is the primary
artifact of the whole project** — a dropped field is amnesia. Test it with
replay diffs (§9).

## 7. Decisions

### 7.1 Cadence — three layers

1. **Dawn plan** (once per simulated day, one batched call): each entity picks a
   `focus` from `duty | earn | socialize | rest`. Focus goes into the prompt.
2. **Tick decisions** (per tick, batched over all idle entities): choose the next
   goal. A tick is 10–20 simulated minutes; a day is 06:00–22:00.
3. **Micro-steering** (free): travel, arrival, eating, transactions, payroll.
   No provider calls.

**Level of detail:** entities far from the camera/player and not in a critical
role may decide every 3rd tick. Prefer criticality (is this entity holding up a
supply chain?) over pure distance; measure both if time permits.

### 7.2 Gating rules (implement as data, test them)

| Action | Offered when |
|---|---|
| `work` | always, for an entity with a trade; label it with the duty ("bake bread") |
| `buy_food` | `hunger > 0.4` **or** carrying food |
| `restock` | missing a recipe input **and** a supplier with stock exists (or water at the well) |
| `rest` | `energy < 0.45` |
| `socialize` | `social < 0.75` |
| `patrol` | role == guard |
| `wander` | role == child **or** nothing else is offered |
| **override** | `hunger > 0.8` and food is carried or affordable from a stocked seller → offer **only** `buy_food` |

Never offer an action whose prerequisite is absent (nobody sells wheat, nobody
is present to talk to). A futile retry loop burns a whole simulated day.
When an urgently hungry villager has no affordable food, record a shortage rumor
and allow their other feasible actions. A villager at maximum hunger with no
meal available can receive emergency relief without attempting a new purchase.

### 7.3 Confidence escalation

The escalation metric applies to valid model decisions at dawn and during ticks.

- `sampled` (default) uses the probability of the sampled action.
- `margin` uses the difference between the two highest probabilities.
- `entropy` uses one minus the Shannon entropy normalized over all gated options.
  A single available option has confidence 1.

If the metric is below `DECISION_MIN_CONF`, use the scripted policy for that
decision and log `escalated: true`. The decision log's `confidence` field
continues to record the sampled probability. The daily summary and live HUD
show escalation count and percentage across all decision attempts in their
respective reporting periods.
- Stretch: route low-confidence social decisions to a text model for a line of
  dialogue. Never let that path affect the world state.

### 7.4 Prompt/state construction

Per entity, compose a compact instruction (~60–120 tokens):

```
<name> the <role>, at <place>. Gold <n>g, carrying <items>. Hunger 0.42,
energy 0.31, social 0.55. The village relies on <name> to <duty>.
Today's focus: <focus>. Recent: <memory>. It is 09:20, weather rain.
```

Shared world summary goes in `state` (time, weather, places). Entity detail goes
in `instructions` — that is what lets one call answer many entities.

## 8. Economy (deterministic; the provider never touches it)

Reference chain:

```
farmer --wheat--> baker --bread--> innkeeper --stew--> villagers
                     ^                  ^
                  water (well)      water (well)
woodcutter --wood--> smith (forge)     herbalist --herbs--> town
guard: daily wage      child: allowance from a parent
```

- Recipes: `baker: 1 wheat + 1 water -> 2 bread`;
  `innkeeper: 1 bread + 1 water -> 1 stew`.
- Trades are **person to person**: buyer travels to the seller's workplace,
  pays the listed price, stock moves. Reject if buyer's gold < price or stock
  is 0.
- Wages/institutional demand at fixed times of day keep secondary trades alive
  (reference: noon and 18:00).
- **Invariants** (assert every tick): no negative gold, no negative stock, total
  gold conserved except explicit wages/allowances, every entity has a location.
- **Caps**: per-item stock ceilings so hoarding cannot silently starve the loop.
- **Deadlock guards**: scheduled clearing/demand events the provider cannot
  override; optional credit (IOU) if a loop deadlocks twice.

## 9. Determinism and replay

- Fixed tick; **no wall-clock in any decision**; no `random` without a seed.
- PRNG stream per `(seed, day, tick, entity_id)` so an extra entity cannot shift
  another's draws.
- Persist every decision: `{day, tick, entity, question_id, action,
  probabilities, confidence, provider, seed, state_hash, escalated}` → JSONL.
- Append world events in emission order within each tick, before that tick's
  state hash.
- Compute a canonical state hash (sorted-key JSON → SHA-256) per tick; log it.
- `village replay decisions.jsonl` verifies the ordered events and per-tick hash
  sequence, and reports the first differing event when one exists.
- Different seeds must produce materially different runs (compare trade counts;
  identical outcomes mean gating or sampling is broken).

## 10. Observability

- Human timeline on stdout: `09:20 anna buys wheat from dorn for 4g`.
- `--explain <entity>`: print the exact serialised instruction and the
  distribution for that entity's last decision.
- End-of-day table: gold, meals, stock per entity; trades; meals; calls;
  latency p50/p95; fallback and escalation rates.
- `--quiet` for batch runs; JSONL is always written.

## 12. Acceptance criteria (these are the definition of done)

- **A1 Offline run.** `--provider scripted --days 3` completes, exit 0, no
  network, no unhandled exception.
- **A2 Model run.** With a reachable endpoint, ≥95% of decisions are answered by
  the provider (fallback <5%), and p95 decision latency stays under the tick
  budget (e.g. 2 s for a 20-minute tick — latency is not the constraint).
- **A3 Living economy.** Per simulated day: ≥8 person-to-person trades, ≥4 bread
  produced, every entity eats ≥2 meals, invariants hold every tick.
- **A4 Determinism.** Same seed twice → identical state-hash sequence. Different
  seeds → trade counts differ by ≥10%.
- **A5 Provider swap.** Changing `DECISION_PROVIDER` alone switches between
  System One, scripted and replay; no source edits.
- **A6 Gating tests.** Unit tests prove: hunger 0.9 offers only `buy_food`;
  no supplier ⇒ no `restock`; energy 0.9 ⇒ no `rest`; guard gets `patrol`,
  baker does not.
- **A7 Replay.** `village replay` from a logs file reproduces the final state
  hash exactly.
- **A8 Auditability.** Every decision line carries the full probability
  distribution; `explain` shows the exact instruction sent.

## 14. Test plan

- `fixtures/fake_systemone.py`: stdlib HTTP server that serves `/v1/models`,
  `/openapi.json` and canned `/v1/systemone` answers (including a malformed
  answer and a 500) so provider tests are hermetic.
- Unit: gating table, trade rejection, recipe consumption, caps, need decay,
  hash stability.
- Property: for random worlds, invariants never violated after 1,000 ticks.
- Contract: provider returns probabilities for every question; missing answers
  cause escalation, not a crash.
- Golden run: a fixed seed + scripted provider committed as a fixture; replay
  must match byte-for-byte.

## 17. Risks (from a prior-art review)

- **State fidelity is the top risk, not latency.** Anything omitted from the
  serialiser is amnesia; stale or duplicated facts contradict each other with no
  exception to debug. Treat the serialiser as the primary artifact.
- **Herding.** Conformity rises with perceived peer confidence — do not put other
  entities' confidences in an entity's state, and diversify goals.
- **Economic deadlock / hoarding.** Locally rational stockpiling starves
  production; caps plus scheduled demand, not provider goodwill.
- **Determinism drift.** Pin the provider, model alias and sampling temperature;
  record them in the log header.
- **Provider edge cases.** Unreachable endpoint, slow first call (model warm-up
  ~2 s), malformed answers. All three must degrade to scripted, not crash.
